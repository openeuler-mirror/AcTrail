# 长时间运行下的资源保留与请求失配问题

## 当前结论

本文记录当前工作树的代码结论。最初确认的 eBPF socket sequence map 泄露、
流式 response 跨 request 消费、response-first HTTP 错配、LLM 明文组装本地容量缺失，
以及成功 response 的时间启发式配对均已修复。

确定性的 request link、stream close、reorder gap 和 truncation/partial 隔离已经补齐。当前没有
仍被代码确认的“对象生命周期已经结束、状态却永久无法释放”的泄露。剩余问题分为两类：

- LLM open/pending 队列和若干按连接、按 stream 的状态表缺少完整的数量、idle 或 close 边界，
  在 close 信号丢失等异常路径中，单条长 trace 仍可产生无界或线性状态保留；
- HTTP/LLM 链接投影器仍保留整条 trace 的动作和索引。

现有 10 轮真实 xiaoo E2E 证明正常路径和 response-first 路径正确，独立 Codex
V2 E2E 也已验证 WebSocket 两轮 exchange 精确配对，但尚未执行隔离的
50～100 轮、多 trace 资源高水位测试。因此尚未量化剩余状态的增长斜率、峰值和 trace 结束后
回落速度。

## 已完成修复

### eBPF socket sequence 生命周期

`payload_socket_stream_sequences` 已接入统一 fd 生命周期。close、close_range、dup 覆盖、
exec、进程退出和重复 connect 都会删除对应 generation 的 inbound/outbound sequence；状态创建
限制为被观测 trace，map 更新失败会 fail-local 丢弃并计数。9000 次连接压力后相关 socket
payload maps 均回落为 0。

因此，文档旧版本中“eBPF sequence map 仍是 P0 泄露”的表述已经失效。

### LLM 明文组装第一阶段边界

LLM 组装器已经具备启动时校验的单流 byte/segment 上限。截断、partial operation 和容量超限
会局部终结 in-flight response/call、隔离损坏方向，并在可信 HTTP 边界恢复；正常消费后释放
buffer/range 的历史 capacity。

刷新默认配置的真实 xiaoo 10 轮和低容量故障 E2E 均通过。reorder gap 和精确
stream close 已接入确定性生命周期信号；尚未实现的容量、idle 和 TTL 后备治理依计划留给
50～100 轮长测决定。

### HTTP response-first 有界补配

outbound socket payload 使用 syscall entry 时间，inbound 使用完成时间。HTTP tracker 以
`(trace, process, fd generation, HTTP/2 stream id)` 保存有界 request/response 双队列；
response action 先提交时，可在配置的 lateness 内由因果上更早开始的 request 补配。

request/response 容量或 response lateness 耗尽会隔离当前 stream，不会通过任意删除队首把
错误扩散到后续 exchange。

### 成功与失败 LLM response 精确配对

成功 response 的 `take_open_request_for_response` / `select_open_request_before` 时间启发式已经
删除。成功与失败响应都使用 `HttpExchangeTracker` 给出的 response→request identity：

- HTTP/1 request 使用 method、target 和 payload sequence range；
- HTTP/1 response 使用 payload sequence range；
- HTTP/2 使用唯一 stream id；
- 任一 identity 缺失时保持未关联，不能消费另一个 open request；
- 流式 response 首次确认后固定绑定 request，终态、finalize 和 forget 清理绑定；
- HTTP identity 先到时进入有界确认队列，容量复用
  `semantic_retention.l2_http.exchange.max_pending_responses_per_stream`。

最终真实 xiaoo 10 轮得到 12 个 request、12 个 response、12 个 call，其中 `/v1`→404 一次、
SSE 200 十一次，并覆盖 response-first 迟到补配。每个 call 的 HTTP response id、该 response
指向的 HTTP request id、LLM request method/path/sequence 和 LLM response 保存的 request
identity 均一致。

## 已修复：缺失 response 后的 HTTP/LLM 错配

### 触发条件

HTTP/1 没有跨方向可直接比较的协议 request id，合法 pipeline 本身也是 FIFO。若 request A
已进入 HTTP tracker，但 response A 因采集 gap、解析 reset 或其他观测缺口完全没有形成 HTTP
action，随后 request B 和 response B 正常到达，当前队列可能把 response B 配给 A。

因果时间只能排除“response 早于 request 开始”的不可能组合，不能区分以下两种情况：

1. 合法 pipeline：A、B 两个 request 均在途，当前 response 确实属于 A；
2. response A 已丢失，当前 response 实际属于 B。

成功 LLM response 现在严格信任 HTTP tracker 的 exchange identity。因此 HTTP 层一旦在上述
场景给出错误 identity，LLM 层仍可能精确地执行这个错误结论。不能在 LLM 层重新使用时间、
“最近请求”或双向 sequence 猜测来修补。

### 当前信号路径

`PayloadSegmentReorderer` 仅对具备连续 sequence 契约的 `Syscall + socket-syscall` 流传播已确认
gap；TLS/seccomp 等非连续 sequence 不会被误判。truncation、partial、failed 或 operation 字节数
不完整会走同一隔离边界。HTTP tracker 隔离整个对应 transport stream，LLM 终结/清除旧关联，
HTTP/1、HTTP/2、body retention 和 protocol memo 同步局部 reset。

eBPF 在每次 socket FD identity 释放时发出独立的内部 release 事件，携带
`trace + process + fd + generation`。它与只表示最后一个 open-file 引用关闭的网络 close observation
分离，因此 close、close_range、dup 目标覆盖、exec CLOEXEC 和进程退出 sweep 都能清理准确的
syscall payload stream。daemon 在同一 collector batch 的 payload 处理完成后再执行 close 清理，
不会先删掉同批次已经采集的尾段。

### 已采用的修复边界

信号来自实际 payload 生命周期路径，不依赖解析 `stream_key` 或新增请求配对启发式：

- reorder gap 在首个 gap 后段上携带 direction 和精确 stream identity；
- fd release 直接携带同一精确 stream identity；
- HTTP tracker 收到 discontinuity 时隔离整个 transport stream，后续 response 保持未关联；
- LLM assembler 终结 in-flight 状态并进入可信边界恢复；
- HTTP/1、HTTP/2 analyzer、body retention gate 和 protocol memo 同步删除或隔离相同 stream。

运行期必须 fail-local。若没有观测到 gap 或 close，就没有证据判断 response 是否丢失；此时只能
保持协议 FIFO，不能为了“恢复”而猜测删除某个 request。

## P1：LLM open/pending 队列无界

`LiveLlmProjector.open_requests` 和 `pending_responses` 按 stream 保存完整或接近完整的
`SemanticAction`，目前没有 per-stream/per-trace 数量上限和 idle TTL。正常配对、trace
finalize 或 forget 会清理，但以下场景会使状态长期滞留：

- LLM request 已识别，HTTP request 或最终 HTTP exchange identity 未形成；
- LLM response 已识别，HTTP response action 因解析缺口未形成；
- identity 存在但 payload range 或 HTTP/2 stream identity 无法证明对应关系。

精确配对修复刻意不再消费不确定候选，因此避免了错配，但也使缺失 identity 时的滞留更加明确。
`confirmed_http_exchanges` 已有界；`open_requests` 和 `pending_responses` 仍无界，而且 reconcile
需要在队列中查找精确候选，队列增长也会增加匹配成本。

修复应与 stream lifecycle 共用一套配置和淘汰语义：

- 配置 per-stream 和 per-trace entry 上限；
- 容量淘汰或明确 discontinuity 时，将已有 call 终结为 partial/error；
- pending response 淘汰不能消费其他 request；
- idle TTL 必须可配置且足够保守，不能误伤合法长 SSE；
- 记录 eviction 原因和高水位，不在 payload 热路径做全表扫描。

## 已修复：正常关闭 stream 的用户态状态按 identity 清理

正常 socket FD 生命周期现在会同步清理：

- reorder 与 socket admission 状态；
- HTTP exchange queue/quarantine；
- LLM assembly、open/pending/confirmed exchange 和 active response binding；
- body retention memo、HTTP/2 probe；
- protocol memo、HTTP/1 buffer 和 HTTP/2 connection。

若内核 transport 丢失 release 事件，状态仍只能等 trace forget；是否需要为这种异常路径增加
容量和 idle 后备边界，留给 50～100 轮资源长测决定。

## 已修复：LLM request→HTTP request link

历史三份真实 xiaoo 10 轮 trace 均稳定缺少 request link。当前实现不再对 outbound request 做
stream 历史候选匹配，而是在 HTTP request/response 与 LLM request/response 四方 identity
确认后直接生成 observed link。

- 12 条 `llm.call.request`；
- 12 条 `llm.call.response`；
- 12 条 `llm.response.http_message`；
- 12 条唯一 `llm.request.http_message`。

call 的配对仍然正确，因为 call 保存精确 HTTP response action id，而 HTTP response 保存精确
HTTP request action id；严格 E2E 也直接核验了 LLM request method/path/sequence 与该 HTTP
request 一致。但 request→outbound HTTP request 的直接观测 link 缺失，使查询、UI 导航和
“完整观测链”不完整。

最新真实 xiaoo 10 轮同时验证每条 request link 的 child id 等于对应 HTTP response 保存的精确
request id；没有新增 link role 或 contract。

## 已修复：WebSocket LLM exchange 精确配对

Codex Responses WebSocket 路径没有每轮 HTTP request/response，只有一次 HTTP Upgrade 握手。旧实现
把每条 WebSocket 消息投影为 HTTP 形状，但整条连接共用同一合成 stream；启用精确 HTTP
exchange 后，这些 request/response 因没有可用的 HTTP exchange identity 而留到 trace close。

WebSocket 适配器本身已维护单个活跃 response 状态。现在每个 `response.create` 使用连接内递增
exchange identity，对应的 completed/failed/incomplete 终止消息复用同一 identity。LLM 层仅对
这种明确标记且唯一的合成 stream 生成 call，不使用 FIFO/时间猜测，也不会把 Upgrade 握手
伪造成每轮 HTTP link。

独立 `probe_codex_llm` 保留两组 complete request/response/call，四条 call link 均唯一有效。
同时修复了 `actrailctl launch` 的幂等清理：子进程退出已自动终结精确 trace 时，后续
`track_remove` 的 `not_found` 不再把正常子进程退出码覆盖为 1。

WebSocket connection 的合成 exchange 还使用连接内唯一 prefix 管理生命周期。TLS payload
truncation、WebSocket close frame 或解码失败删除 connection 时，适配器同步返回该 prefix；LLM 层在
处理同批终止响应后，精确清理该 prefix 下的 assembly、open/pending、confirmed exchange 和 active
binding。非 WebSocket TLS payload 创建的空 process entry 也会立即回收。

socket FD identity 与 TLS object identity 之间当前没有可证明的关联信号，因此底层 FD close 仅精确
清理 syscall socket stream，不猜测性删除 TLS/WebSocket stream。TLS/WebSocket 使用上述自身确定性
truncation/close/error 信号和 trace finalize 回收。

## P2：link projector 的长 trace 线性保留

`HttpMessageLinkProjector` 保存所有可链接的 HTTP/LLM action、stream index 和 emitted link
identity，直到 `forget_trace`。同一 stream 的候选查找会枚举历史 key，因此内存至少随动作数
线性增长，累计匹配成本可能接近二次方。

`LlmExchangeLinkProjector` 会移除部分已完成 call 候选，但未匹配 action 和 emitted identity
仍可保留到 trace 结束。精确 HTTP exchange identity 已经提供了更可靠的 request/response
链接来源；完成 exchange 后应尽早淘汰完整 action body，只保留必要的紧凑 identity，并为异常
未匹配项增加数量边界。

## P2：payload reorder pending 缺少显式容量

`PayloadSegmentReorderer` 的正常 gap 等待窗口为 50ms，idle stream retention 为 60 秒；这些
常数目前硬编码。pending 由等待窗口持续排空，正常流量下不会无限保留，但没有显式 entry/byte
上限。异常高频重复 sequence 或窗口内突发仍可形成较高峰值。

修复应把窗口、retention、单流 pending entries/bytes 设为启动时校验的配置，并记录 gap、
late drop、capacity drop 和高水位。容量故障只丢弃/隔离当前 stream，同时发出 P0 所需的
discontinuity，不能让下游继续把缺口两侧当成连续字节流。

## 隔离长测要求

完成上述生命周期与队列边界后，应使用真实 xiaoo 和刷新的默认 AcTrail 配置运行 50～100 轮，
并至少执行 2～3 条串行 trace。配置、工作目录、socket、pid、SQLite、日志、export 和 xiaoo
trace database 必须使用唯一临时路径。

至少记录：

- actraild RSS、fd、线程数，以及每轮/每 trace 高水位和结束后回落；
- eBPF payload maps 的 entry 数，确认既有回收不回归；
- LLM streams/open/pending/confirmed、HTTP stream queues、reorder pending、body gate、
  analyzer 和 link projector 的状态数量；
- SQLite 中 HTTP request/response、LLM request/response/call 数量与完整 identity 关系。

正确性不能只比较数量。每个成功 exchange 至少满足：

1. LLM call 保存唯一 LLM request、LLM response 和 HTTP response action id；
2. HTTP response 保存唯一 HTTP request action id；
3. LLM request 的 method/path/payload identity 与第 2 项 HTTP request 一致；
4. LLM response 的 request identity 与第 2 项一致；
5. `/v1` 404 和 `/v1/chat/completions` 200 形成独立 exchange；
6. request→HTTP request 与 response→HTTP response 的直接 observed links 均存在且唯一。

RSS 单调增长只能作为信号，不能单独证明泄露。必须结合内部状态数量、trace 结束后的回落和
heap/profile 证据定位实际所有者。

## 建议处理顺序

1. 完成隔离的 50～100 轮、多 trace 资源长测，量化异常路径的状态高水位和回落。
2. 仅在长测证明有必要时，为 LLM open/pending 和按 stream 状态表增加容量、idle 与 eviction 语义。
3. 仅在长测证明有必要时，为 reorder pending 增加配置化容量和高水位；gap 传播已经完成。
4. 利用精确 exchange identity 缩短 link projector 生命周期，减少整 trace 线性保留。
